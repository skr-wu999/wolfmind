# 事件驱动回合调度迁移方案

日期：2026-10-13。状态：**所有者批准，已实施并验收**。

所有者已批准本方案及第 9 节推荐取舍。任务登记使用幂等 Lua，之后单独 XACK；
登记后崩溃由同一 taskId 收敛。POLLING 回退复用新规划器/持久化任务，不再调用旧同步 GameDriver。
具体契约见 agent-runtime.md §4 与 redis-schema.md §16。

后续清理（2026-10-13，所有者批准）：旧 GameDriver 兼容入口、Bean、投票池及接口层 SpeechPacing
已删除。测试复用应用层规划/超时用例或真实事件调度器，POLLING 回退仍走同一调度器。

验收证据：backend engine 118 + server 674 项，0 失败/错误，1 项性能基准跳过；
Redis 集成测试实际运行。新增两组调度测试共 18 项；前端 379 项与类型检查通过，
可执行 JAR、Compose 配置和 UTF-8 无 BOM 检查通过。详见 TASKS 本轮记录。
未调用付费模型、未重启运行中的应用。首版单实例，不宣称多实例分片已实现。

## 1. 目标与现状

用已提交领域事件触发 AI 回合，移除正常路径中每 200ms 查询 RUNNING 对局并执行
GameDriver.step 的行为。领域继续决定行动资格、发言顺序、阶段推进和胜负；
Function Calling 继续只负责一次 Agent 回合内部的查询与行动。

改造前的代码中（历史背景，非当前运行路径）：

- WolfMindConfiguration.gameDriverScheduler 单线程扫描，逐局同步调用 step。
  scheduleWithFixedDelay 的 200ms 是整轮扫描结束后的间隔；普通 AI 决策会占用扫描线程。
- GameDriver 同时承担行动者选择、AI 派发、投票并发、发言阅读停顿、超时跳过、阶段推进。
- Game.handle 在处理行动后执行 runUntilStable，通常同一次命令就生成下一窗口/阶段事件。
  Game.advance 是没有输入时的领域推进入口。load 仅恢复已提交状态。
- 发言等顺序窗口有 TURN_GRANTED；夜间提名、查验、用药和投票不能统一只依赖该事件。
- RedisEventStore 已存领域事件，但当前发布器为进程内实现，没有真正接入 cg-agent 消费组。
- cg-agent 的旧设计把“记忆失败可忽略”和“行动触发”混在同一 ACK 规则内，需明确区分。

实施范围为单服务实例内的可靠调度。使用现有 Redis、SQLite 和有界线程池，
保留游戏规则、领域事件载荷、REST/WebSocket 协议和现有归档/广播路径。
多实例分片部署另行设计，不以本次实现声称已经支持。

## 2. 正常链路

```text
真人或 AI 提交命令
  → 应用服务 → Game.handle / Game.advance
  → 提交状态与领域事件
  → Redis game:{id}:events
  → cg-agent 消费者（每局按事件版本顺序处理）
  → 回合规划器：核对当前权威状态，生成任务和截止时间任务
  → 持久化任务后 ACK
  → 有界执行器领取任务
  → AIControllerAdapter → AgentRuntime → Function Calling → ToolGateway
  → 应用服务提交命令 → 下一批领域事件
```

事件消费线程只做规划和入队，不等待模型完成。模型执行不持有对局写锁。
派发前和提交时分别校验当前窗口、控制者、资格和截止时间；提交仍通过应用服务及 Game。
调度任务是可恢复的运行数据，不是第二份游戏状态，不决定规则结果。

## 3. 哪些事件触发哪些工作

| 事件 / 场景 | 调度行为 |
| --- | --- |
| TURN_GRANTED | 为当前发言、遗言、猎人等顺序窗口建立任务和超时任务；必须与当前状态匹配 |
| PHASE_CHANGED → NIGHT_WOLF | 建立本阶段待行动队列，保持现有狼人逐个派发语义；真人未行动时按当前规则等待截止 |
| WOLF_KILL_NOMINATED | 核对仍处于同一夜间窗口，唤醒下一位待行动座位；已提名的座位不再派发 |
| PHASE_CHANGED → NIGHT_SEER / NIGHT_WITCH | 为仍有行动资格的角色创建任务；无人需要行动时调用领域推进入口 |
| PHASE_CHANGED → DAY_VOTE | 为全部尚未投票的 AI/BOT 创建任务，并发执行；真人等待客户端提交 |
| PLAYER_VOTED | 对已完成任务收敛；不重复派发其他已建任务；阶段切换依赖领域产生的事件 |
| PLAYER_CONTROLLER_CHANGED | 取消旧控制者任务；当前仍可行动且转为 AI 时建立接管任务；转为真人停止 AI 派发 |
| GAME_FINISHED / GAME_ABORTED | 取消未完成任务与定时任务，停止订阅并释放 Agent 和调度资源 |
| GAME_STARTED / GAME_RECOVERED | 注册对局事件流；恢复时根据当前状态补建有效任务，不执行历史失效窗口 |
| WOLF_CHAT_SENT | 可更新角色可见上下文，不创建新的行动任务，不重置预算 |

同一批事件可能包含多个瞬时阶段。消费者读取当前权威状态后，只规划仍有效的窗口，
不执行历史 PHASE_CHANGED 指向的已结束阶段。读取最新状态不能跳过尚未 ACK 的事件处理。
为兼容正在运行的旧局，支持从当前状态和历史窗口锚点补建任务。

## 4. 任务身份、并发与预算

建议新增内部任务类型与存储端口，名称为实施建议，可在契约阶段调整。

任务至少包含：taskId、gameId、playerId、seatNo、phase、round、windowId、
controllerGeneration、dispatchVersion、readyAt、deadline、status、attempts、
leaseOwner、leaseToken、leaseUntil、resultEventIds、lastErrorCode。
不保存未授权完整事件、角色全集、完整 prompt 或模型私有推理。

- windowId：顺序回合使用对应 TURN_GRANTED 的事件版本；阶段行动使用进入该阶段的
  PHASE_CHANGED 事件版本。它是内部窗口锚点，不能当成 aggregateVersion 或公开 phaseVersion。
- taskId 由 gameId、windowId、playerId、controllerGeneration 确定；控制者变更代次由已提交
  PLAYER_CONTROLLER_CHANGED 的版本派生。同一事件重投、另一人投票、狼人夜聊都不会生成新任务。
- dispatchVersion 是首次派发绑定的聚合版本，单独存储。重试、预算和命令身份不因读取新状态重置。
  需要贯通 TurnSignal、TurnRequest、ToolSession、TurnBudgetLedger 和服务端命令幂等键。
- 状态为 READY → RUNNING → SUCCEEDED / WAITING_DEADLINE / EXPIRED / CANCELLED。
  领取带租约和 fencing token；只有当前领取者可提交，旧领取者迟到必须被拒绝。
- 普通顺序窗口每局一个有效模型任务；投票各座位并发，写入仍按现有应用服务串行仲裁。
  跨局使用同一个有界执行池，第一版沿用现有默认 8 的并发上限并设有限队列。
- 队列满时任务保留 READY，不丢弃、不在消费者线程调用模型。到期任务优先由独立超时通道处理。
- 模型失败沿用本回合既有修复与兜底预算；调度器不因每次唤醒重跑整套模型调用。
  进程崩溃留下 RUNNING 任务时，先核对已提交事实；结果不确定时进入规则兜底或等截止，
  第一版不自动重复付费模型调用。预算尝试需在执行前持久化，失败也计入额度。

成功事件是完成依据。提交成功、任务结果记录失败时，恢复通过当前待行动状态与相关已提交事件
收敛，不另选动作。不同工具名也不得绕过“一窗口一次成功行动”。
服务端提交前窗口核验须与应用服务持有写锁后的校验衔接，避免仅派发前校验的时间差。

## 5. 超时与阅读停顿

截止时间来自已提交 TURN_GRANTED / PHASE_CHANGED，旧事件按已保存规则和 occurredAt 恢复。
不在重启、派发或读取时重设截止时间。

- 事件到达时登记对应窗口的到期任务，真人和 AI 都登记。
- 采用一次性定时唤醒；Redis ZSet 持久化到期索引，重启按索引恢复。
  允许周期性检查到期索引并恢复丢失的唤醒，仅对到期条目加载对局。
- 到期工作通过 TimeoutApplicationService 调用 Game.timeoutSkips，再逐条 handle、提交、发布。
  与真人/AI 同时提交发生冲突时重新加载，若该窗口已完成就结束，不强行跳过下一窗口。
- 到期处理使用独立有限执行资源，不等待 AI 线程腾出位置。
- 保留发言阅读停顿：readyAt 由已提交 PLAYER_SPOKE 的 occurredAt 和现有配置计算，
  用定时唤醒取代每 200ms 检查；readyAt 不延长 deadline。
- 到期或接管时停止相关模型/预览；取消不能保证底层请求立即停止，因此迟到写入仍须校验。

## 6. 可靠消费与恢复

新增 EventConsumptionPort 和 TurnTaskStorePort 等内层端口，Redis 细节留在 infrastructure。
Redis cg-agent 使用 XREADGROUP 阻塞读取、PEL 重读/接管、幂等任务登记和 XACK；
具体 API 按当前 Redis/Spring Data Redis 版本核对后实现。

ACK 条件改为：该事件所需任务、取消操作和定时登记已可靠保存，或已经核实事件过期/无需调度。
登记失败不 ACK。登记成功、ACK 失败时重复消费，由 taskId 收敛。
Redis 适配器尽量用同一次 Lua 操作完成任务登记与 ACK，避免不同存储间的双写缺口。
记忆更新仍可重建、失败可告警，但不能因此吞掉行动调度失败。
基础设施故障退避重试；坏事件有限重试后记录死信/告警，不只 ACK 后遗忘，
须确保对应截止任务可恢复，或明确暴露无法规划的阻塞状态。

每局一个 Stream，需要额外处理“如何发现新局”：

- 开局提交成功后注册事件流并唤醒消费器；Redis 保存流目录，首次追加和目录登记原子完成。
- 启动时用流目录/现有 GameIdCatalog 分页恢复订阅，排除 room/user 流，核对当前运行状态。
- 低频目录校对用于补偿提交后进程退出导致的注册通知丢失；只发现/修复订阅，
  不作为普通回合推进方式。历史存量流在迁移启动时建立目录。
- cg-agent 从 0-0 创建以保留历史处理语义；旧历史逐批读取，只执行当前有效窗口。
  已有组先处理 PEL，再读取新消息；禁止从 $ 开始遗漏有效开局窗口。
- 新流注册须能更新阻塞读取的流集合；按流分组设有界读循环，不为每局创建无限线程。
- Redis 模式恢复任务和到期索引；memory 模式提供同语义的可控测试适配器，
  不承诺内存模式跨进程保存任务。恢复过程不调用 Game.replay 以外的模型逻辑。

## 7. 改动范围与实施顺序

| 步骤 | 组件 / 文件 | 完成条件 |
| --- | --- | --- |
| 1. 明确契约 | 本提案、agent-runtime.md、event-design.md、redis-schema.md、tool-gateway.md | 明确事件覆盖、窗口身份、任务字段、ACK、预算、提交 fencing；标出与旧设计差异 |
| 2. 拆分当前驱动 | 从 interfaces/rest/GameDriver 提取 application 中的 TurnPlanner、TimeoutApplicationService、调度编排；兼容入口已在后续清理中删除 | 模型替身验证应用层的行动顺序、超时、投票及阅读停顿 |
| 3. 内存事件链路 | EventConsumptionPort / TurnTaskStorePort、内存适配器、有界执行器、可控时钟 | 禁用扫描后九 AI 完成整局；真人/AI 混合、接管和重复事件验证通过 |
| 4. Redis 可靠接入 | RedisEventStore 流目录、消费器、任务/到期存储、PEL 恢复、装配 | 提交与发布之间崩溃、登记与 ACK 间崩溃、模型运行中重启、写后崩溃均安全收敛 |
| 5. 切换与回归 | WolfMindConfiguration、配置模板、部署示例、TASKS 与相关文档 | 默认事件模式，无普通对局扫描；旧模式可显式回退；后端/前端必要回归通过 |

切换配置建议为 wolfmind.game.driver.mode=POLLING / EVENT_DRIVEN；每个进程只激活一种派发器。
本轮切换和回退均采用停服/重启流程：停止领取、等待或取消在途工作、恢复当前有效窗口。
不在活跃窗口内热切换，不同时运行两套派发器。第一版可以保留 POLLING 作短期回退，
其中已存在的派发去重也须复用稳定窗口任务身份，避免回退重复提交。

## 8. 验收清单

自动化使用固定时钟、模型替身和 Redis 集成测试，不依赖付费 LLM。

1. 关闭 RUNNING 对局扫描，九 AI 经原生工具交互完成终局；回放结果与实时状态一致。
2. 覆盖狼提名、预言家、女巫、投票、发言、遗言、猎人，消费历史瞬时阶段不误派发。
3. 同一事件重复投递/ACK 失败、夜聊、其他人的投票不增加本座位模型调用或重置预算。
4. 八个 AI 投票并发，真人未投不阻塞 AI；写入事件版本连续。
5. 模型一直阻塞时，独立超时通道仍能推进该局；迟到模型、旧租约和旧控制者提交被拒。
6. 一局模型缓慢不占用其他局的事件消费；在并发额度内另一局仍能及时派发。
7. 就绪队列满时任务保留并最终执行或依法超时，没有丢任务/无限线程/忙循环。
8. 崩溃发生在提交后通知前、任务登记后 ACK 前、领取后执行前、行动提交后结果登记前，
   重启后既不漏当前窗口，也不重复成功行动；不重新执行已完成旧回合的模型。
9. 截止时间和阅读停顿在重启后沿用原起点；终局/接管正确清理资源。
10. 旧局缺失某些窗口 deadline、旧消费组 PEL、新局动态注册、超过 100 局的分页恢复均覆盖。
11. AI 只收到座位授权视图；日志/任务存储不泄漏隐藏角色与模型私有推理。
12. 新增指标：事件积压/PEL、任务排队与执行时延、租约恢复、重复抑制、超时执行延迟、死信。
    运行真实模型时另记录调度延迟，不把模型生成耗时计作纯调度性能。

## 9. 已批准决策

所有者已批准下列推荐方案；备选保留作决策记录：

| 决策 | 推荐 | 备选与影响 |
| --- | --- | --- |
| 夜间/投票事件覆盖 | 消费现有 PHASE_CHANGED 与行动事件，在应用层规划合法任务 | 为所有座位新增 TURN_GRANTED：涉及公共事件、并行窗口及隐藏身份暴露审查，改动更大 |
| cg-agent ACK | 任务可靠登记后 ACK；记忆失败与派发失败分开处理 | 保持旧“失败只告警”：无法保证当前回合一定被触发 |
| 窗口身份 | 内部 windowId / taskId 与聚合 expectedVersion 分离 | 用最新聚合版本去重：夜聊/并发投票可能引起同一窗口重复派发 |
| 运行中崩溃恢复 | 查已提交事实；不确定的模型尝试走既有规则兜底/超时 | 自动重跑模型：需要更复杂的持久化预算与付费调用重试政策 |
| 首版部署 | 单实例、多个对局并发；同 Redis 存任务与事件 | 多实例分片：另需对局归属租约、消费者转移、全局并发配额设计 |

此方案保持游戏规则，内部调度和 cg-agent ACK 契约按本次批准迁移。
